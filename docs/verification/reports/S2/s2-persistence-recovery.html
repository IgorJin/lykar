Итоговый контракт

Сохранение Draft теперь является атомарной идемпотентной операцией. Клиент фиксирует точный batch до отправки, сервер связывает результат с actor, project и draft, а stale revision требует явного решения пользователя.

1 · Persist
key + expected revision + exact operations сохраняются в sessionStorage.
2 · Validate
capability проверяется, payload канонизируется и хешируется.
3 · Commit
operations + revision + result записываются одной транзакцией.
4 · Recover
same key replay или reconciliation по operation IDs снимает batch.
same actor/project/draft + same key + same payload
  └─ 200 original result, replayed=true, zero duplicate effects

same scope + same key + different payload ──► 409 IDEMPOTENCY_CONFLICT
new key + stale expectedRevision           ──► 409 REVISION_CONFLICT
                                                 │
                                                 └─ preserve pending → explicit review

S2-04.1 · Save contract

  • URL-safe key, 16–160 chars.
  • Canonical SHA-256 включает revision, operations и snapshot.
  • Result хранится минимум 30 дней; migration forward-only.

S2-04.2 · Atomic retry

  • Draft row lock сериализует конкурентные saves.
  • Одна транзакция для effects, revision и result.
  • Capability проверяется раньше lookup сохранённого result.

S2-04.3 · Client recovery

  • Recovery envelope v2 хранит pending и in-flight batch.
  • Lost response сверяется с remote operation IDs.
  • Новые edits во время fetch не входят в подтверждённый batch.

S2-04.4 · Conflict UX

  • Нет silent rebase и last-write-wins.
  • Reload сохраняет local pending operations.
  • Новый key создаётся только после явного review.
