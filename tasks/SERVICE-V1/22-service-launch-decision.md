# SERVICE-V1-22 — Решение о готовности сервиса

Status: PLANNED
Priority: P0
Depends on: SERVICE-V1-21
Parallel wave: W20
Can run in parallel with: None

Stage: E7 — Пилот и решение об открытии сервиса
Planning date: 2026-10-02

## Goal

Зафиксировать готовую границу первой версии и понятное решение о запуске.

## Problem solved

Набор закрытых задач не равен подтверждённой готовности обслуживать внешних клиентов.

## Enables

- Отдельное осознанное открытие сервиса.
- Следующую очередь улучшений по evidence пользователей.

## Scope

- Сверить outcomes E1–E7, pilot issues, supported install path, operational ownership и customer docs.
- Проверить воспроизводимую регистрацию → подключение → быструю правку → Deploy/Disable/Rollback и альтернативный A/B-link/report path.
- Зафиксировать ограничения, support/incident procedure, limits и оставшиеся PROPOSED решения; обязательные вопросы закрыть до запуска.
- Принять решение: готов к открытию / продолжить ограниченную бету / блокирован конкретными причинами.
- Подготовить reviewable release checklist и действия публикации; внешнее открытие/публикация остаётся явным действием владельца при исполнении.
- Будущие AI/billing/CMS/автоцели/обычный A/B трафик/X1-X2 сформировать отдельно, не добавляя их как скрытые gates.

## Parallel execution

Один владелец финального решения; public deployment и пользовательские коммуникации не автоматизируются планировщиком.

Hard prerequisites: SERVICE-V1-21. Все транзитивные prerequisites обязательны. Изменение общей схемы/контракта/lockfile или использование одного mutable стенда требует последовательного checkpoint.

## Acceptance criteria

- [ ] Каждый release-blocking критерий имеет evidence; нет незакрытых обязательных tests или внешних prerequisites.
- [ ] Decision явно различает техническую приёмку, пилот и доступность публичного сервиса.
- [ ] Указан точный candidate/asset set, provider/config решения и поддерживаемая матрица.
- [ ] Неуспешный пилот либо непроверенный restore не превращается в DONE ради завершения плана.

## Checks

- `AGREED` — `UI`: UI и ручная приёмка: desktop/mobile, клавиатура, фокус, ошибки, сохранность правок и диагностика подключения.
- `AGREED` — `RELIABILITY`: Надёжность, безопасность и performance: потеря/задержка сети, исходная страница при сбое, отсутствие дублей аналитики, изоляция доступа, consent, лимиты запросов, отсутствие токенов в логах; измерение доставки/replay и согласование новых численных бюджетов до реализации.
- `AGREED` — `OPS`: Эксплуатация: тестовая среда, реальные тестовые письма, обновление версии, резервная копия/восстановление, фоновые задачи и сигнал о сбое.
- `AGREED` — `COMMANDS`: Используем существующие npm run build/typecheck/test, test:e2e:http, test:e2e:browser, Playwright и временную PostgreSQL; новые команды отмечаем как будущие.

Точная привязка согласованных слоёв к этой задаче:
- `AGREED` — Review всех групповых reports и task-to-test mapping; повтор smoke только если candidate/config менялись.
- `AGREED` — Финальная ручная проверка cold-start клиентского пути и наличия ответственного за эксплуатацию.

Необходимый environment и evidence — в [TEST-PLAN.md](./TEST-PLAN.md). Новые suites/commands сначала создаются в рамках scope; отсутствие команды не трактуется как успешная проверка.
